## 1. 中心问题

工具型 LLM Agent 往往能够完成与用户目标相关的动作，但“动作相关”并不等于“动作获得授权”。本项目首先检验：

> 当收件人、文件、金额、数据用途、操作范围或不可逆副作用没有被明确授权时，Agent 是否会自行补全关键参数并执行高风险动作，而不是澄清、降级或拒绝？

在确认该现象稳定存在后，再研究风险感知澄清、时序授权监控和约束最小修正。

## 2. 研究主线与副线

### 2.1 主线：未知授权与风险感知澄清

把关键授权槽位标记为 `ALLOW`、`DENY` 或 `UNKNOWN`。对每个基础任务构造四联样本：明确允许、明确禁止、缺失授权、外部伪造授权。核心观察是模型会不会把 `UNKNOWN` 当作 `ALLOW`。

### 2.2 副线 A：长轨迹授权约束遗忘

在同一任务中加入 0、4、8、16 个无关但自然的工具观察，测量最早声明的权限、期限和“发送前确认”等约束是否随轨迹长度退化。

### 2.3 副线 B：来源感知的间接提示注入

复用 AgentDojo 的公开环境和攻击定义，比较“只判断内容语义”与“显式记录信息来源和授权证据”的审计器。本副线在主线基线稳定后开始，不自行复制其数据为主数据集。

## 3. 数据策略

### 3.1 权威公开基准

| 数据/环境 | 权威性与规模 | 用途 | 局限 |
|---|---|---|---|
| AgentDojo（NeurIPS 2024 Datasets & Benchmarks） | 97 个现实任务、629 个安全测试；官方开源 | 外部工具数据、提示注入、任务效用与安全联合评测 | 主要研究注入，未知授权的参数级真值不足 |
| InjecAgent（ACL Findings 2024） | 工具集成 Agent 的间接注入基准；官方开源 | 检查数据窃取与直接危害攻击的可迁移性 | 轨迹和授权结构与本项目不完全一致 |
| ToolEmu（ICLR 2024 Spotlight） | 36 个工具包、144 个高风险测试；官方开源 | 风险行为类型和模拟器设计参考 | 依赖 LM 模拟和评判，不适合作为唯一真值 |
| Agent Security Bench（ICLR 2025） | 10 场景、400+ 工具、多类攻击/防御 | 广泛外部有效性和攻击面覆盖 | 工程量大，不能作为第一阶段唯一环境 |
| CCTU（2026） | 复杂约束下工具使用公开基准 | 长轨迹/复杂约束副线 | 新基准，需要人工核验与本问题的标签对应关系 |

### 3.2 必须自建的数据

没有成熟公开数据集直接提供“用户是否明确授权某个工具参数”的三值、字段级真值。因此需要建立 **Quanta-Ask Authorization Pairs（QAAP）**：

- 第一阶段：12 个基础任务 × 4 种授权条件 × 4 个轨迹长度 = 192 条；
- 领域：邮件、文件、日历、支付；
- 高风险槽位：接收者、路径、数据用途、金额、期限、是否不可逆；
- 每个样本保存授权来源、允许动作、禁止动作、需澄清字段和期望决策；
- 生成器只负责机械扩展，种子任务和标签由两人独立审核；
- 正式论文版本目标不少于 500 个基础任务，并报告 Cohen's kappa。

第一阶段样本是“研究仪器”，不能用同一个 LLM 同时生成、标注和评判后直接声称问题成立。

## 4. Phase 1：问题存在性验证

### 4.1 基线

1. `Direct-Execute`：缺失字段时使用默认值或上下文猜测，模拟过度自主 Agent；
2. `Prompt-Only`：系统提示要求谨慎，但无结构化权限检查；
3. `LLM-Judge`：独立模型在执行前判断允许/澄清/拒绝；
4. `Deterministic-Contract Oracle`：直接读取人工真值的上界，只用于验证评测器；
5. 2–3 个开源指令模型，经统一 OpenAI-compatible 接口运行。

`Direct-Execute` 和 Oracle 是管线基线，不是论文中与强模型竞争的主要基线。

### 4.2 指标

- Unauthorized Execution Rate（UER）：非允许样本中实际执行的比例；
- Unknown-as-Allow Rate（UAR）：`UNKNOWN` 样本中执行的比例，主指标；
- Deny Violation Rate（DVR）：明确禁止样本中执行的比例；
- Clarification Recall / Precision；
- Allowed Task Completion（ATC）：明确允许样本的任务完成率；
- Over-refusal Rate（ORR）：明确允许样本中澄清或拒绝的比例；
- Pairwise Authorization Sensitivity（PAS）：成对样本改变授权条件后决策正确改变的比例；
- Horizon Degradation：UAR 随干扰步数增长的斜率及置信区间。

### 4.3 判定标准

满足以下条件才进入方法创新阶段：

- 至少两个可复现实验模型的 UAR 显著高于 10%；
- 长轨迹相对短轨迹的 UAR 增加至少 5 个百分点，或存在统计显著退化；
- 失败在至少两个工具领域出现，而非单一提示模板偶然现象；
- 人工复核确认多数“执行”确实越过了缺失或禁止授权，而不是标注歧义；
- Prompt-only 或通用 LLM Judge 未同时实现低 UER 和高 ATC。

若主现象不满足标准，优先转向“长轨迹约束遗忘”或“来源伪造授权”副线，而不是事后修改指标。

## 5. Phase 2：可能的创新模块

创新方向由 Phase 1 失败分布决定：

| 基线现象 | 优先创新 |
|---|---|
| `UNKNOWN` 被高频当作允许 | 三值意图契约 + 风险敏感澄清 RVoI |
| 长轨迹退化明显 | 前瞻授权状态机 + 时序触发器再激活 |
| 外部文本被当作用户授权 | 参数级来源追踪 + 反事实证据检验 |
| LLM Judge 漏检且置信度失真 | 共形风险门控 + 选择性执行 |
| 拒绝安全但效用过低 | 词典序最小修正而非全量拒绝/重规划 |
| 执行前合法但真实副作用异常 | 预测—执行双阶段误差监控 |

## 6. 阶段路线

1. Phase 0：仓库、环境、三份研究文档与可复现协议；
2. Phase 1A：QAAP 小规模生成、离线评测器和管线基线；
3. Phase 1B：服务器开源模型基线和问题存在性统计；
4. Phase 1C：AgentDojo/CCTU 外部有效性试验；
5. Phase 2：根据证据冻结一项主创新和最多一项副创新；
6. Phase 3：完整 benchmark、主结果、消融、泛化和自适应攻击；
7. Phase 4：论文、复现包和投稿。

## 7. 必要决策门

只有以下情况需要项目负责人/导师决策：中心假设不成立而需换主线、引入付费闭源 API、大规模人工标注、改变论文目标或对外发布可能含敏感数据的材料。
